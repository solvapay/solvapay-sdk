An **MCP App** is a UI resource that an MCP host loads inside a sandboxed iframe. Host sandboxes typically block direct HTTP calls to arbitrary backends, so the UI cannot hit your API the way a normal React app would.

The TypeScript SDK ships a dedicated surface for this environment. `<McpApp>` from `@solvapay/react/mcp` mounts the whole thing; under the hood `createMcpAppAdapter` returns a `SolvaPayTransport` that tunnels every write through `app.callServerTool` instead of HTTP, and reads come off the bootstrap payload the server sends with each intent-tool result. Every hook (`usePurchase`, `useMerchant`, `<CurrentPlanCard>`, `<LaunchCustomerPortalButton>`, etc.) works unchanged.

## Prerequisites

- An MCP host such as [`basic-host`](https://github.com/modelcontextprotocol/basic-host)
- A SolvaPay product with at least one active plan
- An MCP server that implements the SolvaPay tool surface — see [MCP Server integration](/sdks/typescript/guides/mcp) for the server-side paywall patterns
- `@solvapay/react` and `@modelcontextprotocol/ext-apps` installed in your MCP App bundle

## Install

```bash
pnpm add @solvapay/react @modelcontextprotocol/ext-apps
```

## Quick start

Render `<McpApp>` and you're done. It runs `app.connect()`, applies host theme / fonts / safe-area insets, fetches the bootstrap payload, mounts `SolvaPayProvider` with the MCP transport, and routes the payload's `view` to the matching surface.

```tsx
import { createRoot } from 'react-dom/client'
import { App } from '@modelcontextprotocol/ext-apps'
import { McpApp } from '@solvapay/react/mcp'
import '@solvapay/react/styles.css'
import '@solvapay/react/mcp/styles.css'

const app = new App({ name: 'my-app', version: '1.0.0' })

createRoot(document.getElementById('root')!).render(<McpApp app={app} />)
```

Pass `applyContext` if you want to handle host theme and insets yourself, and `views` to override an individual surface. See [`examples/typescript/mcp-checkout-app/src/mcp-app.tsx`](https://github.com/solvapay/solvapay-sdk/blob/main/examples/typescript/mcp-checkout-app/src/mcp-app.tsx) for the full wiring.

### Customizing the surface

Two escape hatches, in increasing order of control:

- **Override one surface.** Pass `views={{ checkout: MyCheckout }}` to `<McpApp>`. The other surfaces keep the SDK implementation.
- **Own the layout.** Render `<McpAppShell bootstrap={…}>` or `<McpViewRouter>` plus the per-view primitives (`<McpCheckoutView>`, `<McpAccountView>`, `<McpTopupView>`) inside your own tree.

`<McpApp>` remains responsible for connecting the app, fetching the bootstrap payload, and seeding the hook caches from it. That seeding is load-bearing: because the adapter implements no read methods, `usePurchase`, `useMerchant`, `useProduct`, and `usePlans` have nothing to render until the payload lands. Bypassing `<McpApp>` entirely means reimplementing that bootstrap, so prefer the two hatches above.

## Tool contract

The adapter is **write-only**. Every read the UI needs — merchant, product, plans, purchase, payment method, balance, usage — arrives on the `BootstrapPayload` that each intent tool returns on `structuredContent`, and `seedMcpCaches` from `@solvapay/react/mcp` primes the hooks' module-level caches from it. The transport therefore never fetches reads, and the old per-read tools (`check_purchase`, `get_merchant`, `get_product`, `list_plans`, `get_payment_method`, `get_customer_balance`, `get_usage`) no longer exist.

Import `MCP_TOOL_NAMES` from `@solvapay/mcp-core` (also re-exported from `@solvapay/react/mcp`) so client and server stay in lockstep. It is **not** exported from `@solvapay/mcp`.

### Transport tools (called by the adapter)

| Transport method        | MCP tool name                 | Returns                      |
| ----------------------- | ----------------------------- | ---------------------------- |
| `createPayment`         | `create_payment_intent`       | `PaymentIntentResult`        |
| `processPayment`        | `process_payment`             | `ProcessPaymentResult`       |
| `createTopupPayment`    | `create_topup_payment_intent` | `TopupPaymentResult`         |
| `attachBusinessDetails` | `attach_business_details`     | `{ taxBreakdown }`           |
| `activatePlan`          | `activate_plan`               | `ActivatePlanResult`         |
| `cancelRenewal`         | `cancel_renewal`              | `CancelResult`               |
| `reactivateRenewal`     | `reactivate_renewal`          | `ReactivateResult`           |
| `createCheckoutSession` | `create_checkout_session`     | `{ sessionId, checkoutUrl }` |
| `createCustomerSession` | `create_customer_session`     | `{ sessionId, customerUrl }` |

### Intent tools (called by the host or the model)

These are the only tools whose descriptors carry `_meta.ui.resourceUri`, so they are the only ones that open the iframe. Each returns a `BootstrapPayload` stamped with the `view` the shell should render.

| MCP tool name    | `view`     | Surface                                 |
| ---------------- | ---------- | --------------------------------------- |
| `upgrade`        | `checkout` | Plan picker + payment                   |
| `manage_account` | `account`  | Current plan, card, cancel / reactivate |
| `topup`          | `topup`    | Credit top-up amount picker             |

Unimplemented tools surface as a thrown error from the adapter — catch and feature-detect in your component.

## Server side

`createSolvaPayMcpServer` from `@solvapay/mcp` registers every transport and intent tool, the UI resource, and the Stripe CSP baseline for you. Merchant tools go in `additionalTools`; you never hand-register a commerce tool.

```ts
import { createSolvaPayMcpServer } from '@solvapay/mcp'
import { z } from 'zod'

const server = createSolvaPayMcpServer({
  solvaPay,
  productRef: process.env.SOLVAPAY_PRODUCT_REF!,
  resourceUri: 'ui://my-app/mcp-app.html',
  htmlPath: './dist/mcp-app.html',
  publicBaseUrl: 'https://my-mcp.example.com',
  additionalTools: ({ registerPayable }) => {
    registerPayable('search_knowledge', {
      schema: { query: z.string() },
      handler: async ({ query }, ctx) => ctx.respond(await search(query)),
    })
  },
})
```

Pair it with `createMcpOAuthBridge` from `@solvapay/mcp/express` (or the turnkey `createSolvaPayMcpFetch` from `@solvapay/mcp/fetch`) to surface `customer_ref` on `extra.authInfo`. A complete working server lives at [`examples/typescript/mcp-checkout-app/src/server.ts`](https://github.com/solvapay/solvapay-sdk/blob/main/examples/typescript/mcp-checkout-app/src/server.ts).

If you are registering tools on a hand-rolled `McpServer` instead, use `registerAppTool` and `registerAppResource` from `@solvapay/mcp` — they are vendored there because `@modelcontextprotocol/ext-apps` has no SDK v2 server build. Import `RESOURCE_MIME_TYPE` from the same place rather than hardcoding the MIME string.

## Authentication

Because the real identity lives server-side on the OAuth bridge's `customer_ref`, the provider only needs a sentinel token to flip `isAuthenticated` true. `<McpApp>` installs that adapter for you — nothing to configure.

If you mount `SolvaPayProvider` yourself, supply the equivalent alongside the transport:

```tsx
const mcpAuthAdapter = {
  getToken: async () => 'mcp-session',
  getUserId: async () => bootstrap.customer?.ref ?? null,
}

<SolvaPayProvider config={{ auth: { adapter: mcpAuthAdapter }, transport }}>
  <CheckoutPage />
</SolvaPayProvider>
```

Without an adapter, the provider short-circuits the fetch pipeline and the transport never runs.

## Hosted checkout from inside the iframe

Open checkout in a new browser tab. Pre-fetch the session URL on mount and render a real `<a target="_blank">` anchor — scripted `window.open` after an async round-trip is blocked by typical host sandboxes, but anchor clicks are permitted.

```tsx
import { useEffect, useState } from 'react'
import { useSolvaPay } from '@solvapay/react'

function UpgradeButton({ productRef }: { productRef: string }) {
  const { _config } = useSolvaPay()
  const [href, setHref] = useState<string | null>(null)

  useEffect(() => {
    if (!_config?.transport) return
    _config.transport
      .createCheckoutSession({ productRef })
      .then(({ checkoutUrl }) => setHref(checkoutUrl))
      .catch(err => console.error('checkout session failed', err))
  }, [_config, productRef])

  if (!href) return <button disabled>Loading…</button>
  return (
    <a href={href} target="_blank" rel="noopener noreferrer">
      <button>Upgrade</button>
    </a>
  )
}
```

On `focus` / `visibilitychange`, call `refetch()` from `usePurchase` so returning from the hosted tab flips the card to its new state automatically.

## Account management

Once a customer has paid, drop `<CurrentPlanCard />` into the tree and the SDK does the rest — plan name, next-billing line, payment-method summary, plus **Update card** and **Cancel plan** actions. The card returns `null` when there is no active purchase, so you can render it unconditionally. The MCP `manage_account` view passes `hideUpdatePaymentButton` and `hideCancelButton` and pairs the card with a single **Manage account** customer-portal CTA — both flows run through the portal there.

```tsx
import { CurrentPlanCard, LaunchCustomerPortalButton } from '@solvapay/react'

function Account() {
  return (
    <>
      <CurrentPlanCard />
      <LaunchCustomerPortalButton />
    </>
  )
}
```

- **`<CurrentPlanCard />`** renders the active plan, mirrored card brand/last4, and inline **Update card** / **Cancel plan** actions. The MCP `manage_account` view hides both — card updates and cancellation route through the **Manage account** customer-portal CTA — and surfaces a one-line hint pointing at it.
- **`<LaunchCustomerPortalButton />`** opens the hosted customer portal in a new tab (default label: "Manage account"). The button renders enabled from first paint and fetches the portal URL in the background; multiple instances under the same provider share a single in-flight `createCustomerSession` round-trip. When the URL has resolved, click is a real `<a target="_blank">` navigation (sandbox-safe). On a cache-miss click the handler awaits the in-flight promise and falls back to `window.open`.
- **`usePaymentMethod()`** exposes the mirrored card under `{ paymentMethod, loading, refetch }` when you need to build a custom account view. The card brand and last4 come from the `payment_intent.succeeded` webhook persisted on the Customer — no card-element iframe required inside the MCP App sandbox.

## Text-only paywall

The MCP App surface uses SolvaPay's **text-only paywall**. When a `registerPayable` tool is gated it emits a plain-text narration on `content[0].text` that names the recovery intent tool — "You're out of credits. Call the `topup` tool to add more", "You don't have an active plan for this tool. Call the `upgrade` tool to pick a plan" — with the structured gate on `structuredContent` for programmatic consumers. No UI meta is stamped on merchant tools, so the iframe never flashes on a silent success.

The model reads the narration and calls the named intent tool, which is what opens the widget. There is no `McpPaywallView` / `McpNudgeView` / `McpUpsellStrip` component anymore.

## Complete example

A full working example — server, client, OAuth bridge, polling, and the five-state purchase flow — lives in the SDK repo at [`examples/typescript/mcp-checkout-app`](https://github.com/solvapay/solvapay-sdk/tree/main/examples/typescript/mcp-checkout-app). Clone it, set `SOLVAPAY_SECRET_KEY` and `SOLVAPAY_PRODUCT_REF`, point `basic-host` at `http://localhost:3006/mcp`, and you have an end-to-end paywalled MCP App running locally.

## Known boundaries

- **`trackUsage` stays on the server.** Usage metering belongs on your backend, not the client — continue to call `solvaPay.trackUsage(...)` from `@solvapay/server` inside your tool handlers.
- **Inline card entry on Claude.** Claude's MCP Apps host applies a fixed sandbox Content Security Policy that does not forward the spec's `frameDomains` declaration. Because Stripe's card surfaces load in a nested iframe, the inline Payment Element cannot render inside Claude's widget. The SDK detects this at runtime and falls back to SolvaPay-hosted checkout in a new tab (see [Hosted checkout from inside the iframe](#hosted-checkout-from-inside-the-iframe)), so checkout still completes and the payment stays on SolvaPay's rail. On hosts that honor the spec (e.g. ChatGPT), the inline Payment Element renders directly — no configuration needed.
